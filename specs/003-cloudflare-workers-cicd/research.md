# Research: Деплой і надійність

## R1: Публічний URL без імені акаунта
- **Decision**: Змінити акаунт-субдомен `*.workers.dev` через DELETE + PUT на `byndevav`.
- **Rationale**: PUT не працює, поки субдомен існує (помилка 10036); dashboard API вимагає сесію.
- **Alternatives**: власний домен (платно/довга реєстрація), залишити старий subdomain (не задовольняє вимогу).

## R2: TLS для нового субдомена
- **Decision**: Не оголошувати деплой готовим, поки `https://...` не відповідає 200.
- **Rationale**: Cloudflare може видавати сертифікат для `*.<subdomain>.workers.dev` хвилинами або годинами.
- **Alternatives**: тимчасово повернути старий субдомен — ризик зламати вже змінені URL.

## R3: Зберігання обкладинок
- **Decision**: D1, оригінальні байти з перевіркою magic bytes, ліміт 1.5 МБ.
- **Rationale**: R2 на акаунті вимагає картки; `sharp` не працює у workerd.
- **Alternatives**: R2 (платно), WebP-перекодування (немає енкодера у Worker).

## R4: Швидкість
- **Decision**: Закріпити схему константами, паралелізувати D1-читання, кешувати публічні обкладинки з ETag.
- **Rationale**: Інтроспекція давала ~21 запит на виклик; послідовні await множили latency.
- **Alternatives**: кешувати всю сторінку (ламає персональний вміст), збільшувати план Cloudflare (платно).

## R5: GitHub Actions і токен
- **Decision**: CI + deploy окремими workflow-ами; секрети в GitHub Secrets.
- **Rationale**: Потрібна перевірка кожного PR і автоматичний деплой тільки з `main`.
- **Alternatives**: deploy з локальної машини (не відтворюваний), один workflow на все (менш гнучко).
- **Pitfall**: PAT без `workflow` scope не може пушити `.github/workflows/*.yml`.

## R6: Чистий checkout
- **Decision**: Node-фолбек створює батьківську папку `DATABASE_PATH` рекурсивно.
- **Rationale**: `data/` у `.gitignore`, тому на CI її немає.
- **Alternatives**: комітити порожню `data/.gitkeep` — менш надійно для довільних шляхів.
